# MONOLITH / Архитектура управления сайтом

## Цель

Публичный сайт и панель администрирования используют общую доменную модель проектов, публикаций, медиа, заявок и отзывов. Разделение файлов позволяет заменить статические данные на PostgreSQL без перерисовки интерфейса. **Сейчас база и auth не подключены.**

## Модули и маршруты

| Модуль | Публичные маршруты | Администратор |
|---|---|---|
| Каталог | `/proekty`, `/proekty/[slug]` | `/admin/proekty` |
| Медиа | галереи и hero | `/admin/media` |
| Заявки | `/kontakty`, формы на главной | `/admin/zayavki` |
| Отзывы | `/otzyvy` | `/admin/otzyvy` |
| Контент и SEO | все публичные страницы | `/admin/nastroyki` (проект) |

Код: `src/types/content.ts` — контракты; `src/lib/projects.ts` — временный источник данных; `prisma/schema.prisma` — схема будущей БД; `src/app/api/` — контракты маршрутов. `/admin` — только read-only, в production скрыт middleware, пока нет настоящей сессии.

## Требования безопасности к настоящей админке

1. **Auth.js / Auth.js + собственный identity provider**, проверка сессии **на сервере в каждом обработчике и server action**, а не только в middleware и клиентском компоненте.
2. Роли `OWNER`, `EDITOR`, `VIEWER`, серверный RBAC. Каждая операция проверяет роль. Нельзя давать публичной форме доступ к CRUD администратора.
3. CSRF-защита и cookie `httpOnly`, `secure` (в production), `sameSite`; ограничение попыток входа, обязательные MFA/2FA для владельцев при возможности провайдера.
4. Postgres через Prisma. Миграции, резервные копии, инкрементальный аудит и безопасные восстановления.
5. Загрузка медиа только через разрешённые MIME и ограничения размера, проверка magic bytes, приватные временные файлы, обработка изображений на сервере, storage (S3 / R2 / Blob); хранить `storageKey` и запись в `MediaAsset`. Не доверять исходным именам.
6. HTML пользователя (тексты проектов и отзывов) экранировать, rich text санитизировать, запретить произвольный HTML.
7. Заявки: серверная Zod-проверка, rate limiting, honeypot/Turnstile, журнал согласия и версии политики, ограничение доступа, сроки хранения и возможность удаления по запросу.
8. Отзывы по умолчанию `PENDING`; публиковать только `APPROVED`, хранить модератора и дату публикации; не выдумывать отзывы.
9. Все публикации в формате DRAFT → PUBLISHED → ARCHIVED, предпросмотр черновиков исключительно с проверкой доступа, инвалидация кэша `revalidatePath`/`revalidateTag`.
10. Настройки проекта: реальные контакты, юридическое лицо, политика, мета-теги; изменение SEO данных с ролями и историей.

## Порядок подключения

**Фаза A. База и репозитории:** подключить PostgreSQL, проверить Prisma схему, миграции, seed 6 демо-проектов (3 DRAFT), заменить `src/lib/projects.ts` на серверный `ProjectRepository`. Публичный сайт получает только `PUBLISHED`, где есть `cover`. Текущие `id/slug` сохранить.

**Фаза B. Безопасный вход:** создать настоящую страницу входа, добавить провайдер аутентификации, server guard, RBAC в actions/API. До этого не открывать реальный `/admin` в production.

**Фаза C. CRUD проектов:** формы create/edit, draft/publish, сортировка карточек, галереи, фильтры, SEO, image upload.

**Фаза D. Заявки и отзывы:** endpoints, валидация, защита от спама, notification queue + retries, модерация, журнал действий.

**Фаза E. Управление контентом:** CMS для текста, FAQ, страниц услуг, контактов, мета-тегов, юридических документов; draft preview.

## Профиль маршрутов API

- `GET /api/projects` — опубликованный каталог, уже реализован из статических данных.
- `POST /api/contact` — сейчас возвращает 503 `INTEGRATION_REQUIRED`, не сохраняет персональные данные.
- `POST /api/reviews` — сейчас 503, не сохраняет отзывы.
- Private admin routes/actions — **не реализованы**, до установки RBAC не создавать небезопасные endpoints.

## Важные замечания

До получения юридических сведений не публиковать текущие тексты политики как готовую политику предприятия. Проекты/изображения являются AI-концептами, а не отчётом о выполненных работах. Не указывать вымышленные цены, клиентов, отзывы, адреса и статистику.
